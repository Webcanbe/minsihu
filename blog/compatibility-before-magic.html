Compatibility Before Magic

WebCanBe compatibility engineering · August 2026

Visual editing gets impressive quickly in a demo. Real repositories make the problem much harder.

A component may run on the client, the server, or both. Environment variables may be safe in one place and dangerous in another. A file can look visually simple while depending on framework behavior that a visual editor should not rewrite casually.

Classify before editing

I started designing an Environment Boundary Map and detection rules for WebCanBe. The goal was to identify framework and runtime constraints before deciding what kind of editing the product should allow.

For a Next.js project, that includes boundaries created by server and client components, explicit directives, environment-variable exposure, route behavior, and patterns that the system cannot yet classify confidently.

Unsupported is better than silently wrong

I would rather show that a file is preview-only or code-edit-only than offer a visual control that corrupts the project. That led to a compatibility model instead of a universal-editing promise.

The product can progressively earn support: inspect the repository, classify its boundaries, explain what is safe, and only then expose higher-level manipulation.

Magic becomes trustworthy when its limits are visible

This is a recurring principle in my work. A system feels more powerful when it does not pretend. Explicit boundaries let automation go further because the user can see where confidence ends.
