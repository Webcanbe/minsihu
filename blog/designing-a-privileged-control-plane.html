Designing a Privileged Control Plane

WebCanBe AdminKey · August 2026

Administrative actions are different from ordinary product actions. They can affect users, data, deployments, or system state in ways that deserve a narrower interface.

I explored that idea through a separate WebCanBe AdminKey application rather than placing every privileged operation inside the main product.

Separate capability from convenience

The application was built around explicit operation descriptions, manifests, validation, and rendered action details. The goal was to make a sensitive action inspectable before execution rather than hiding it behind a generic button.

I used Swift and XCTest to validate the package and operation-rendering behavior. One useful result from testing was catching a mismatch between the number of supported operation kinds and the number expected by the test suite — a small example of why privileged systems need boring, explicit validation.

Privileged actions deserve friction

For ordinary UI, fewer steps often feels better. For a control plane, some friction is a security feature. The user should be able to see what will happen, which target it affects, and whether the operation matches the manifest before approving it.

The broader lesson is that an admin interface should not simply be the normal product with more buttons. It should have a different trust model.
