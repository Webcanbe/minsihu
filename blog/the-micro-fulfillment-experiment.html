The Micro-Fulfillment Experiment

Earlier marketplace project · 2026

I once explored a marketplace that connected unused local space with sellers who needed distributed storage and fulfillment. At first glance it looked like a simple two-sided marketplace: sellers need space, hosts have space.

That description hid almost all of the real product.

The marketplace begins after the match

Once inventory is physically stored somewhere, the system has to know what arrived, where it is, who is allowed to touch it, how an outgoing order is identified, and how mistakes are resolved.

I started mapping separate seller and host workflows, QR-based inventory and dispatch, role-specific screens, and the operational state changes that connect storage to fulfillment.

The lesson was that the value of a marketplace is rarely the matching screen alone. The difficult part is the shared operating system that lets two parties trust the transaction after they find each other.

Physical systems punish vague software

In a purely digital product, an ambiguous status can be annoying. In logistics, an ambiguous status can mean the wrong item moved to the wrong place. That changes how you think about identifiers, audit trails, confirmation steps, and role permissions.

It also makes the boundary between software and operations obvious. If a process depends on a human scanning a code or physically confirming a handoff, the product has to model that step rather than pretending everything is automatic.

What carried forward

I did not continue the project as my main company, but I kept the systems lesson. Every marketplace has an invisible workflow graph. If that graph is weak, more users only make the failure larger.

That perspective later influenced how I think about WebCanBe’s marketplace and workspace ideas: discovery matters, but reuse, verification, permissions, and repeat workflows are where a platform becomes durable.
